# 打卡连续记录、断签备注与心情补卡

## 状态

Planned

## 目标

优化“热力/打卡记录”体验，让用户即使中途断签，也能清楚看到过去的连续打卡情况，而不是只看到当前连续天数。

本次目标包括：

1. 展示累计打卡总天数。
2. 展示历史连续打卡段，包括每段的开始日期、结束日期、连续天数。
3. 明确标记断签发生在哪一天。
4. 支持对断签日期添加、编辑、删除备注。
5. 提供一个参考现有年度热力图视觉风格的“打卡记录图”，用于直观看到打卡日、断签日和补卡状态。
6. 支持心情补卡：允许为过去某一天补录或修改心情。
7. 保持现有单文件 HTML、本地存储和 GitHub Gist 同步架构，不拆分项目。

## 当前问题

现有习惯打卡强调“当前连续天数”。一旦某天断签，当前 streak 会被重置，用户无法直观看到上一段连续了多少天，也很难知道具体在哪一天断掉。

现有“热力”页已经包含心情、年度热力图、倒计日和打卡记录等子模块入口，适合承载历史打卡分析与补卡能力。

现有代码中还已经存在习惯补卡相关 UI/逻辑结构，以及 `heat` tab 下的 `mood`、`heatmap`、`checkins` 子模块定义，因此本次应优先复用现有数据和交互，不重新设计一套完全独立的打卡系统。

优先定位以下区域，不要全量重读整个文件：

## 产品设计

### A. 打卡概览

在“热力”页的打卡记录区域顶部增加概览信息：

- 累计打卡：X 天
- 当前连续：X 天
- 最长连续：X 天
- 历史断签：X 次

累计打卡按“存在有效习惯打卡记录的自然日”统计，避免同一天完成多个习惯时重复计算为多天。

如果现有产品语义更适合按“某个习惯”查看，则实现时保留可扩展能力，但本次优先实现整体打卡记录视图，不增加复杂筛选器，除非现有结构已经具备。

### B. 历史连续打卡段

根据已有打卡日期排序，计算连续自然日区间。

示例：

- 2026-08-01 ～ 2026-08-12：连续 12 天
- 2026-08-14 ～ 2026-08-20：连续 7 天

若 8 月 13 日没有有效打卡，则该日为断签日。

页面至少显示：

- 连续区间
- 连续天数
- 与下一段之间的断签日期/断签天数

历史 streak 必须由现有每日记录动态计算，不把“连续天数”作为新的永久真值重复存储，避免数据漂移。

### C. 断签记录与备注

断签日定义：位于两个有效打卡日期区间之间、但当天没有有效打卡记录的自然日。

对断签日期支持备注：

- 添加备注
- 编辑备注
- 删除备注

建议新增一个轻量数据字段，例如：

`S.checkinBreakNotes = { "2026-08-13": "出差，忘记打卡" }`

实际字段名以现有 `S` 数据结构命名风格为准。

要求：

- 旧数据没有该字段时自动按空对象处理。
- 不破坏旧版 localStorage 数据。
- 能被现有导出/导入、Gist 同步流程正常携带。
- 删除备注只删除备注，不改变打卡记录本身。

### D. 打卡记录图

在“打卡记录”模块增加一个参考现有年度热力图的可视化记录图。

视觉状态至少区分：

- 正常打卡日
- 断签日
- 补卡日（如果现有数据能区分原始打卡与补卡）
- 未来日期 / 无数据日期

交互建议：

点击某一天，打开日期详情弹层，显示：

- 日期
- 当天是否打卡
- 当天完成的习惯（若现有数据可得）
- 是否属于某个连续打卡段
- 如果是断签日，显示断签备注
- 编辑备注入口
- 如果是过去日期，提供补卡入口

不要重复实现一套和现有热力图完全不同的日期网格；优先复用已有年度热力图的日期生成、格子样式和响应式逻辑。

### E. 心情补卡

支持用户为过去日期补录心情。

要求：

- 可以选择过去日期。
- 如果当天没有心情记录：新增。
- 如果当天已有心情记录：进入编辑而不是创建重复记录。
- 保存后年度热力图/相关心情统计应立即刷新。
- 使用现有心情数据结构，不新建平行的“补卡心情”数据源。
- 如果现有心情记录支持备注或说明，补卡应沿用相同字段；若不支持，本 Task 不额外扩展心情备注。

日期限制：

- 不允许补未来日期。
- 今天仍可以使用现有正常心情入口。

## 数据兼容策略

优先原则：只新增可选字段，不迁移或重写旧记录。

建议：

- 历史连续段、累计天数、最长连续等全部运行时计算。
- 只有“断签备注”需要新增持久化字段。
- 心情补卡直接复用现有心情日期记录结构。
- 若现有习惯补卡已经能区分补卡来源，则复用；如果没有，不为了本次显示而大改历史数据结构。

若 Codex 发现现有数据结构与上述假设不同，必须先汇报，不得自行实施大规模 migration。

## 不允许修改的范围

- 不拆分 `index.html`。
- 不引入 React/Vue/npm 或构建工具。
- 不重构无关模块。
- 不全局格式化文件。
- 不修改与本功能无关的记账、学习、备忘录等业务。
- 不改变现有 GitHub Gist 加密协议。
- 不删除或重命名现有 localStorage 核心字段，除非已有兼容层并明确说明。

## 并行执行说明

建议本次不要一开始就让多台电脑同时改 `index.html`，因为这是单文件项目，冲突概率高。

推荐顺序：

1. 先完成 Task 1 并合并到 `main`。
2. Task 2 完成并合并。
3. Task 3、Task 4、Task 5 理论上可以并行，但由于都可能修改 `index.html` 的热力区域，实际更建议串行执行，或确保各自修改区域非常独立后再并行。
4. 最后执行 Task 6。

优先降低合并冲突，而不是追求并行速度。

## 验证方法

整体完成后至少验证以下场景：

1. 连续打卡 10 天后断 1 天，再连续 5 天：应显示两个连续区间，最长 10 天，断签日期明确。
2. 断签日增加备注，刷新后备注仍在。
3. 对过去一天补心情，热力/心情展示更新。
4. 对已有心情的日期再次补录时进入编辑，不生成重复数据。
5. 跨月连续打卡统计正确。
6. 跨年连续打卡统计正确。
7. 无历史记录时页面不报错。
8. 旧版本 localStorage 数据可直接打开。
9. 导出再导入后断签备注和心情补卡数据仍存在。
10. Gist 同步后另一台设备可以看到相同数据。
