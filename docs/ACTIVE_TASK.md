## 当前目标

**优化连续记录里的断签日期展示，避免断签日越来越多后页面无限拉长。**

## 当前分支

## 背景

阶段 B 的主体功能已经完成并通过 ChatGPT 代码 Review，但人工验收发现一个可扩展性问题：

当前每段连续记录会把所有断签日期直接全部铺开显示。断签日较多时，这一块会越来越长，影响阅读效率。

## 本轮只做

调整 `renderCheckinSegments()` 相关展示逻辑：

1. 每一段断签记录默认只展示最近 3 个断签日期。
2. 如果该段断签日期不超过 3 个，保持全部显示，不出现额外按钮。
3. 如果超过 3 个：
   - 默认展示最近 3 个日期；
   - 增加“展开全部 X 天”入口；
   - 点击后展示该段全部断签日期；
   - 展开后入口变为“收起”；
   - 收起后恢复只展示最近 3 个。
4. 日期按钮原有能力必须保留：
   - 点击日期仍打开 `openCheckinDateDetail()`；
   - 有备注的日期继续显示“有备注”状态；
   - 备注新增 / 编辑 / 删除后重新渲染时仍正常。
5. 默认显示的 3 个日期按“最近优先”展示。
6. 样式保持现有墨白极简风格，移动端不横向撑破。

## 禁止

- 不修改打卡统计语义。
- 不修改 `checkinBreakNotes` 数据结构。
- 不修改 localStorage / 导出导入 / Gist 协议。
- 不修改打卡记录图。
- 不执行阶段 C。
- 不做无关重构或全局格式化。

## 验证

至少验证：

- 断签 1～3 天：全部显示，不出现展开入口。
- 断签 4 天以上：默认只显示最近 3 天，并正确显示剩余数量。
- 展开后可看到全部日期。
- 收起后恢复 3 个日期。
- 展开/收起后日期点击仍能打开详情。
- 有备注日期的标识仍正常。
- 保存/删除备注后列表重新渲染不报错。
